---
name: Gateway OTA update
description: Como funciona a atualização remota do gateway (launcher run.js, rollback, token de download, rota pública)
---

- O serviço (systemd/NSSM) executa `run.js` (launcher), nunca `dist/main.js` direto. O launcher aplica `update/staging` e seta `BLUEBEE_OTA_LAUNCHER=1` (é isso que define `otaSupported` no health). O run.js NÃO é atualizado pela OTA — mudanças nele exigem reinstalação manual.
- Aceite da atualização é SÓ por confirmação: o gateway apaga `update/pending-verify.json` ao reconectar no MQTT. O launcher NUNCA aceita por uptime — se o processo sair com pending presente, ou ficar vivo 10min sem confirmar (watchdog mata), faz rollback e grava `update/ota-result.json` (publicado como `rolled_back` no boot seguinte).
- Download do pacote OTA: rota pública `GET /gateways/update-package?token=` autenticada por token de uso único (consumido no 1º resgate, TTL 15min) + SHA-256 no comando MQTT. **O controller público precisa vir ANTES do GatewaysController no array `controllers` do módulo**, senão `GET /gateways/:id` captura "update-package" e o JwtAuthGuard devolve 401.
- Pacote OTA não tem pasta-base no zip (extrai direto no staging); pacote do agente tem base `bluebee-gateway-agent/` e inclui run.js.
- Progresso OTA vive em memória no backend (GatewayOtaService), mas TRANSIÇÕES de estágio intermediário também são persistidas em otaState/otaAt (sem otaMessage) — é o que permite à varredura expirar OTAs presas mesmo após restart do backend (sweep no banco: otaState intermediário + otaAt velho + sem memória → expired).
- Estágios intermediários sem confirmação por >15min (maior que o watchdog de 10min do launcher) expiram para o terminal `expired` (gerado pelo backend, nunca pelo gateway) — persistido em otaState/otaMessage/otaAt; confirmação tardia via MQTT sobrescreve. `expired` NUNCA grava reportedVersion (a versão alvo não foi confirmada). Guarda do triggerUpdate usa isInProgress (intermediário não-expirado), sem corte fixo de tempo.
- Progresso REPETIDO do mesmo estágio (mesmo commandId) NÃO renova o prazo de expiração — o receivedAt original é preservado no apply(); senão um gateway repetindo "restarting" nunca expira.
- Recuperação manual: `POST /gateways/:id/update/cancel` (ADMIN/CCO, auditado) marca terminal `expired` com mensagem de cancelamento (memória + banco) e libera novo disparo; 409 quando não há intermediário a cancelar.
- Launcher: rollback SEM `previous/dist/main.js` válido grava `ota-result.json` com `status:'failed'` (nunca some em silêncio); o gateway publica `failed` vs `rolled_back` conforme `info.status`. Gateways em campo só ganham consertos do run.js com reinstalação manual.
- Tolerância a EPERM persistente (v1.21.0+): rename que esgota retentativas com erro transitório cai para CÓPIA recursiva (fs.cpSync force, mescla sobre destino existente) + remoção da origem em melhor esforço; só itens CRÍTICOS ao runtime (`dist`, `node_modules`, `package.json`) abortam a atualização — `src`/`tsconfig*`/locks etc. viram `warnings` no pending-verify, que o gateway publica na mensagem do `completed` (backend mostra `error ?? "Atualizado…"` mesmo em completed). Movimentos primários usam orçamento maior (`BLUEBEE_SWAP_PRIMARY_RETRY_ATTEMPTS`, ~45s) que undo/limpeza; mensagem de falha transitória inclui dica OneDrive/antivírus. Fault injection ganhou op `copy`.
- Launcher à prova de brick (v1.19.0+): NUNCA encerra por exceção (handlers globais + try/catch no loop — senão o NSSM entra em crash-loop: "o serviço não retornou um erro"); toda troca de pasta usa retentativas com backoff p/ erros transitórios do Windows (EPERM/EBUSY/ENOTEMPTY/EACCES); `pending-verify.json` só é escrito quando a troca completou DE FATO; falha definitiva no apply desfaz os movimentos (ordem inversa) e mantém a atual; no boot, raiz sem `dist/main.js` é reparada de `previous/` (rollback) ou `staging/` (promove + recria pending p/ verificação normal).
- Testes do launcher rodam o run.js REAL num tmpdir (`apps/gateway/test/launcher-*.spec.ts`): timings via env `BLUEBEE_VERIFY_POLL_MS`/`BLUEBEE_RESPAWN_DELAY_MS`/`BLUEBEE_SWAP_RETRY_*` e falhas simuladas via `BLUEBEE_LAUNCHER_TEST_FAULTS` (JSON `{"rename":{"match":"dist","times":2,"code":"EPERM"}}` — inerte fora dos testes).
- URL de download: montada de `BACKEND_PUBLIC_URL` (prefixa `https://` se vier sem protocolo; usada COMO VEIO, deve refletir a rota pública exata) ou dos headers do request **+ sufixo `/api`** — o host público é o do frontend Next e o backend só é alcançável de fora via o rewrite `/api/*`; sem o `/api` o download cai no Next, que redireciona p/ /login com Location relativo → "Invalid URL" no gateway antigo. Host vazio nos headers é recusado com 4xx (senão `https:///api` parseia com host "api"). Backend valida com `new URL()` e recusa 4xx ANTES de publicar o comando. Gateway resolve `Location` relativo contra a URL original e todos os erros de download citam host/caminho SEM a query (token). Testes do download vivem em `apps/gateway/test/` (fora de src, que é hasheado/empacotado) — rodar com `npx jest --config test/jest-unit.json`.
- A detecção de update compara versões (package.json do apps/gateway vs reportedVersion): mudar código do gateway SEM subir a versão = campo nunca recebe OTA, silenciosamente. Guard: `apps/gateway/scripts/gateway-manifest.mjs` (check hasheia src/agent/config e compara com `gateway-manifest.json`; `--update` recusa regravar sem bump). Registrado como validação `gateway-manifest` — ao mexer no gateway, suba a versão e rode `--update`.

**Why:** rollback precisa funcionar mesmo se a versão nova nem sobe; e o bug 401 da rota pública é silencioso (rota parece existir mas responde Unauthorized).
**How to apply:** ao mexer em rotas estáticas sob `/gateways`, confira a ordem dos controllers; ao mudar formato do pacote/launcher, lembre que gateways em campo só ganham run.js novo via reinstalação manual.
