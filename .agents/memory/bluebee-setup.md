## npm + Replit package firewall: regenerate the lockfile
The Replit registry is `http://package-firewall.replit.local/npm/` (note the `/npm/` path prefix). A committed `package-lock.json` whose `resolved` URLs point to `https://registry.npmjs.org/...` breaks: npm swaps only the host (→ `package-firewall.replit.local`) and drops the `/npm/` prefix, producing 404s on tarballs (e.g. npm-run-path).
**Why:** npm host-replacement doesn't preserve a registry path prefix.
**How to apply:** delete `package-lock.json` and let `npm install` regenerate it against the firewall registry. (`npm view <pkg>` succeeding while `npm install` 404s on the tarball is the tell.)

## Long installs must run inside a Replit workflow, not bash background
Backgrounded processes (`nohup ... &`) from the bash tool get killed when the tool call returns, leaving a half-written `node_modules` (ENOTEMPTY on rename of e.g. `handlebars`). A single foreground run exceeds the 120s bash limit.
**How to apply:** clean `node_modules`, then run install as part of a workflow command (`npm install && exec <dev server>`); the workflow runs uninterrupted. Poll `getWorkflowStatus`.

## Do NOT overwrite the Agent-format `.replit`
This workspace's `.replit` is the new Agent format (`modules`, `[agent]`, `[workflows]`, `[deployment]`, `[[ports]]`). Old-format `.replit`/`replit.nix` from generic guides would break the platform. Run services via Replit workflows instead. Preview port mapping here: localPort `8080` → external `80`, so run the dev server on 8080 (`next dev -p 8080 -H 0.0.0.0`).

## Frontend needs Supabase env to even boot (in mock mode too)
`apps/frontend/src/lib/supabase.ts` calls `createBrowserClient` at module load; it throws if `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` are empty. The auth service imports it, so every route 500s without them — independent of `NEXT_PUBLIC_USE_MOCK`. For a no-real-backend phase, set placeholder values in `apps/frontend/.env.local` (`https://placeholder.supabase.co` + any non-empty key); the client constructs but mock data drives the UI.

## git-delete guard (main agent)
The main agent is blocked from deleting some git-tracked files (`.gitignore` was blocked) — message: "Destructive git operations are not allowed in the main agent." Deleting other tracked files (package.json, lib/) and gitignored `node_modules` worked. `rsync` is NOT installed — use `tar`/`cp` to copy trees. Preserve `.git/` (Replit checkpoints are git commits), `.local/`, `attached_assets/`.

## Backend boot em watch mode: logs não são capturados; verifique por curl
`Start Backend` roda `nest start --watch`; o arquivo de log da workflow só grava a linha `Starting compilation in watch mode...` — os logs do NestJS (rotas mapeadas, "Nest application successfully started") NÃO aparecem lá.
**How to apply:** para confirmar que o backend subiu e uma rota existe, use `curl -s -o /dev/null -w "%{http_code}" http://localhost:4000/<rota>` — um `401` (guard ativo) já prova app rodando + rota registrada; não fique esperando log de boot que nunca vem.

## Dados em modo mock (Fase 1): roteador central no api-client
- TODAS as chamadas de dados passam pelo `src/lib/api-client.ts` (`apiGet/apiPost/apiPatch/apiDelete`). Os componentes/hooks SEMPRE chamam os services → api-client; quase nenhum desvia para mock sozinho. Logo, o único lugar correto para mockar é o api-client, não cada service.
- `src/lib/api-mock.ts` (`mockRequest`) é o roteador: api-client delega quando `NEXT_PUBLIC_USE_MOCK==='true'`. GETs devolvem `mocks/data`/`mocks/handlers`; recursos sem dados (`/projects`, `/scada/projects`, `/alarm-events`, `/alarm-rules`, `/trends`) devolvem `[]` (estado "0 cadastrados" esperado); endpoint de objeto único sem dado (`/projects/:id`) lança erro explícito (não devolver `[]` p/ shape de objeto).
- **Cuidado com mismatch de shape mock↔contrato do service** (a origem real dos bugs): ex. gateways comparam `status==='online'` minúsculo; dashboard `PendingCommand` usa `command`/`status` mas `mockPendingCommands` tem `action` (precisa mapear); `TenantItem` exige `siteCount/deviceCount/createdAt` mas `mockTenants` não tem. Sempre conferir o TIPO esperado pelo service, não só o nome do mock.
- Telas SCADA: o service faz `fromApi(ScadaScreenApi)`; devolva a tela "crua" (mockScadaScreens serve). PATCH `/scada/screens/:id/home` — o `:id` NÃO é o último segmento; casar a rota antes do echo genérico senão o id vira "home".
- Tempo real (socket.io `${SOCKET_URL}/telemetry`) em `useBacnetTelemetry.ts` e `useAlarmEvents.ts` (`useAlarmRealtime`): gated em `USE_MOCK` (early-return) senão geram erro de WebSocket/conexão recusada no console. No mock, `useBacnetTelemetry` seta `initialLoad=false` p/ não travar skeleton.
- Limitação aceita da Fase 1: fetches diretos (sem api-client) só disparados por ação — `projects.getGatewayConfigText`, export CSV de reports, discover BACnet/MQTT — ainda batem no backend e falham se clicados.

## Rotas "faltando" (404) eram módulos apagados por rollback de checkpoint — restaurar do git, não criar placeholder
- Sintoma: `/automation`, `/ai`, `/cco/commands`, `/admin/settings`, `/account` davam 404, mas `sidebar.tsx` as linkava. A tentação foi criar `PlaceholderPage.tsx` — ERRADO: o usuário JÁ havia desenvolvido esses módulos (Chat IA com Claude+RAG+histórico, automação, comandos, settings).
- **Causa real:** um commit de rollback de checkpoint ("Restored to <sha>", centenas de arquivos) APAGOU módulos desenvolvidos. O último commit completo deles ainda era ancestral de HEAD, então recuperável.
- **Escopo TOTAL do estrago (medir antes de prometer):** `git diff --stat <backup> HEAD -- apps/frontend/src` revelou ~109 arquivos afetados: 35 apagados + 74 revertidos p/ versão antiga (e8647bf). Fonte de recuperação confiável: o branch `gitsafe-backup/main` (commit ancestral pré-rollback) tem o trabalho completo. NÃO restaurar a árvore inteira do backup — ela é PRÉ-mock e sobrescreveria o trabalho de Fase 1.
- **Arquivos a NÃO sobrescrever no restore (têm trabalho de mock + feature juntos):** `lib/api-client.ts`, `modules/auth/services/auth.service.ts`, `hooks/useBacnetTelemetry.ts`, `modules/alarms/hooks/useAlarmEvents.ts`, layouts e `sidebar.tsx`. `lib/api-mock.ts` e `mocks/` são SÓ do HEAD (seguros). Como tudo passa pelo api-client, arquivos de feature restaurados continuam roteando pelo mock — basta restaurar + adicionar handlers de mock p/ os endpoints novos.
- **Restauração faseada a pedido do usuário:** 1ª etapa = 3 abas de ADMINISTRAÇÃO (Agente de Gateway `/admin/gateway-agent`, Servidores `/admin/cluster`, Conhecimento `/admin/knowledge` + módulo knowledge + agent-package.service); itens re-adicionados ao sidebar (NAV_ADMIN e NAV_CCO) com ícones Download/Server/BookOpen; mocks p/ `/cluster/status`, `/health/storage`, `/health/storage/tables`, `/knowledge`. 2ª etapa = lote dos ~88 restantes restaurados do backup.
- **ARMADILHA do restore em lote (mismatch HEAD-preservado × backup-restaurado):** o HEAD preservado é `e8647bf` (antigo)+mock; os componentes restaurados são do backup (geração NOVA). Duas formas de quebra: (a) EXPORT faltando → 500 SSR global. Ex.: `useAlarmEvents.ts` HEAD sem `useAcknowledgeAlarmEvents`/`useAlarmEventStats` que `alarms.page` importa. (b) PROP divergente → TypeError client-side ("Cannot read properties of undefined"). Ex.: `dashboard.page` (HEAD) passava `alarms={...}` mas `AdminKpiRow` (backup) espera `alarmsByStatus={alarme,normal,reconhecido}`. **Solução:** para cada preservado, comparar exports (`git show <backup>:p | rg '^export'`) E props que os componentes-irmãos backup esperam; alinhar o preservado às assinaturas do backup, mantendo só o patch de mock (ex.: `if(!enabled||USE_MOCK) return`). NewAlarmModal backup tem `panelHref?` com default → prop extra `onViewPanel` é só ignorada (não quebra).
- **Assets binários do public também somem no rollback:** ex. `bluebee-logo.png` (referenciado em `sidebar.tsx`) e `apple-touch-icon.png` davam 404. Restaurar com `git cat-file -p <backup>:caminho > caminho` (binário; NUNCA `git show`).
- **Banco DEV vazio após rollback:** rollback de checkpoint reverte TAMBÉM o Postgres (`DATABASE_URL`) → `\dt` = "no relations". Na Fase 1 (mock) o frontend NÃO usa o banco (dados vêm dos mocks do front), então não bloqueia. Recriar tabelas = `cd apps/backend && npx prisma migrate deploy --schema prisma/schema.prisma` (cria as 14 tabelas) + `npx ts-node prisma/seed.ts`. GOTCHA: o seed falha com `TS2305 '@prisma/client' has no exported member 'Role'` se o client estiver velho → rodar `npx prisma generate --schema prisma/schema.prisma` ANTES. O `seed.ts` só popula 1 tenant (Autobras) + 1 usuário ADMIN (admin@autobras.com.br); demais tabelas ficam vazias. Dados DEV além do seed (criados manualmente) NÃO são versionados → perdidos no rollback, só recuperáveis voltando a um checkpoint anterior (que também reverte código).
- **Padrão de mock para sockets:** só `useBacnetTelemetry` abre socket.io (hooks SCADA useViewer/useScreenTelemetry/etc NÃO abrem direto, dependem dele). Gating = `const USE_MOCK = process.env.NEXT_PUBLIC_USE_MOCK==='true'` + `if(!enabled||USE_MOCK) return` antes do `io(...)`. Endpoints de mock adicionados no lote: GET `/alarm-groups`, `/scada/simulator/devices`, `/reports/command-history` (vazios); POST `/scada/simulator/ensure` (VirtualDevice vazio). Limite Fase 1 aceito: detalhes/mutações (`/alarm-groups/:id`, `/scada/simulator/:id/points`/`/value`) usam echo genérico sem persistência.
- **Como recuperar (main agent sem git destrutivo):** texto via `git show <sha>:caminho > caminho`; binários (PNG) via `git --no-optional-locks cat-file -p <sha>:caminho > caminho` (NUNCA `git show` em binário — corrompe na saída de texto). Achar o sha: `git log` do módulo antes do rollback. Depois apagar o placeholder órfão.
- **Regra do usuário:** nunca alterar menu/navegação/rotas. Antes de "criar página que falta", verificar no histórico git se ela já existiu — restaurar > recriar.
- Teste autenticado (middleware redireciona tudo p/ login = 307, curl anônimo não valida): `curl -H 'Cookie: bluebee_access_token=mock-token' .../ai` deve dar 200.

## Restaurar módulo do backend pós-rollback: reinstalar deps npm também
Um rollback de checkpoint que apaga um módulo do backend também reverte o `package.json` — então as dependências npm exclusivas daquele módulo somem. Restaurar só os `.ts` (via `git show <commit>^:path`) não basta: também é preciso (a) reinstalar os pacotes faltantes no workspace certo e (b) reregistrar o módulo em `app.module.ts` (imports + array `imports[]`).
**Why:** ao restaurar cluster/health, o `tsc` falhou com `Cannot find module 'pg'` — o `pg`/`@types/pg` haviam sido removidos do `package.json` do backend pelo mesmo rollback; ClusterService usa `Client` do `pg` direto (advisory lock + LISTEN/NOTIFY, que o Prisma não cobre).
**How to apply:** depois de `git show` dos arquivos, rode `npx tsc --noEmit` no app; para cada `Cannot find module`, `npm install <pkg> --workspace apps/backend` (e `-D @types/...`). Só então religar no `app.module.ts` e reiniciar o workflow.

## Restaurar módulo de IA/RAG pós-rollback: requisitos externos + baseline de migrations divergente
- O módulo de IA (Chat IA + base de conhecimento) tem requisitos externos NÃO óbvios pelo código: `ANTHROPIC_API_KEY` (chat via Claude) **e** `OPENAI_API_KEY` (embeddings) — são serviços distintos; o chat degrada sem RAG mas o chat em si exige a chave Anthropic. A base de conhecimento exige a extensão `vector` (pgvector) no Postgres (`CREATE EXTENSION IF NOT EXISTS vector;`) + índice HNSW `vector_cosine_ops` na coluna de embedding. pgvector 0.8.0 está disponível no Postgres do Replit.
- **Why:** decisão do usuário foi usar chaves próprias (não integrações gerenciadas); o serviço lê `process.env.ANTHROPIC_API_KEY`/`process.env.OPENAI_API_KEY` direto.
- **Baseline de migrations divergiu após o rollback:** o branch pós-rollback RE-CRIOU algumas migrations com timestamps NOVOS (ex. user_password_hash/audit_log) enquanto as migrations de IA/KB apagadas tinham timestamps ANTIGOS (folders fora de ordem). Ao restaurar, criar UMA migration nova com timestamp atual (não reusar os folders antigos fora de ordem) concatenando o SQL original. Essa migration de restauração NÃO é idempotente (CREATE TYPE/TABLE/INDEX sem IF NOT EXISTS) → **risco ao promover p/ staging/prod que já tiveram as migrations antigas de IA/KB**: tratar baseline (`migrate resolve`) antes de `migrate deploy` lá.
- **How to apply:** após `git show` dos arquivos + reinstalar deps (`@anthropic-ai/sdk`, `openai`) + merge dos modelos no schema atual (com relações em User/Tenant) + religar no app.module → `prisma migrate deploy && generate`, pedir as 2 chaves via environment-secrets, reiniciar. Teste e2e real: login devolve `accessToken` (não `access_token`); `POST /ai/chat` espera campo `content` (não `message`) e deve dar 201 com `{reply,conversationId,...}`.

## Skeleton de carregamento ≠ telemetria em tempo real (telas de detalhe de device)
Nas telas de detalhe de device (BACnet/Modbus/MQTT), a lista de pontos (nome/tipo/instância/unidade) chega SÍNCRONA via prop `device` (= `selectedDevice` da lista já carregada em `devices.page.tsx`); não há fetch assíncrono de pontos no componente. O único dado pendente é o VALOR em tempo real (telemetria via socket), que tem feedback próprio por linha ("Aguardando leitura..."). MQTT/Modbus já renderizam a tabela direto, sem skeleton de tela cheia.
**Why:** o BACnet tinha um skeleton de tela cheia atrelado a `initialLoad` da telemetria (`initialLoad && connected`), escondendo dados estruturais já carregados por até 10s e causando flicker tabela→skeleton→tabela (porque `connected` vira true após o 1º render). Com 0 pontos, ainda atrasava o empty-state em 10s.
**How to apply:** não condicionar um skeleton de tela cheia ao `initialLoad` da telemetria. Renderize a estrutura disponível imediatamente e use feedback por célula só onde o dado realmente falta. Skeleton de tela cheia só quando NÃO há nada estrutural para exibir (e isso vem de um carregamento assíncrono real, não da telemetria).
